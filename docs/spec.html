Flight Plan
Design spec v0.3 14 Oct 2026 Built · tested · installed on this Mac

See where Claude is, and change course mid-flight.

Flight Plan is a live map that sits beside your Claude Code chat. It draws the whole job as a route of waypoints, puts a small plane on the step Claude is on, and lets you click any step or choice to change it.

Built for people who build with Claude without reading every tool call: you see what's done, what's next, and what Claude decided for you, in plain words.

Item 1 · Why

What people lose track of today

#1

The plan drifts from reality. To-do lists stop updating; nobody can tell which step the agent is on. It was the most common complaint across every tool we looked at.

Cursor forum (5+ threads), Claude Code issue #48189, community kanban viewers built because their authors "had no idea what was happening"
#2

Edits get lost or wait for the whole run. Changing one step means re-planning everything, or a message that lands only after the agent finishes.

Claude Code #10602 and duplicates; Cursor plan edits ignored on Build; Codex steer queued to the end
0

Tools that combine all of it. A live map, a "you are here" marker, plain language, and click-to-change that reaches the running agent. Fun visualizers exist (Pixel Agents, ~88k installs) but show activity, not position in a plan.

Survey of Devin, Cursor, Replit, Copilot, Windsurf, Cline, Codex, Jules, Kiro, Lovable and ~15 Claude Code community projects
Item 2 · How it flies

Claude files the plan; the map watches the work

Flight Plan is a Claude Code mod: a small plugin that draws a pane in the desktop app and gives Claude one tool, route. Claude files the route once, naming each step's files and how it will check them. From then on the map moves the plane on what it actually sees: each file Claude writes, each test it runs, and Claude's own progress reports.

Item 3 · Test flights

What Phase 0 found, and what changed

We ran five real tasks twice as independent Opus 5.5 sessions (a greeter, a to-do module, a signup page, a Markdown converter, a saved to-do app), with an early version of the mod watching every call. Total cost about $3.30.

QuestionAnswerEvidence
Does Claude file a plan before it starts editing?Yes10/10 runs
Do the files it declares match the files it writes?Yes35/35 writes
Does it work through steps in plan order?Mostly9/10 runs
Does it report each step boundary itself?No1/5 routes closed, even with nudges
Does it read and apply your edits?Usually2/3 acknowledged
Does it obey "the user removed this step"?Yesskipped the file, told the user why

Opus 5.5 plans, writes all its files in one burst, runs the tests, and answers. Its natural checkpoints are much coarser than the steps it plans. So asking it to report every step was the wrong foundation.

The design change

  1. The plane moves on evidence. The first write to a step's declared files moves the plane there; a passing test marks the steps it covers "checked". Claude's own reports still count, but the map no longer waits for them. It still never moves on a guess, and never backwards past work it saw.
  2. Your edits take the fast lane. A change rides back on Claude's very next tool result, seconds after you click, worded "finish what you're doing in this step, then apply this".
  3. Some hooks are closed to mods. A built-in security layer keeps mods out of the system prompt and the stop hook. Flight Plan's instructions ride your messages instead, and the end of a turn is reconciled on the map: anything Claude didn't close is shown as such, with a one-click "ask Claude to update the map".

Replaying all ten recorded runs through the evidence tracker put the plane on the right step after every write; 29 of 36 steps finished in the right state, and the seven misses had known fixes, now built in.

Item 4 · Changing course

What happens when you edit mid-flight

Your change lands on the map the moment you click, and it wins over Claude's version. Claude finishes the step it's on (no half-edited files), then re-plans around you. One control can stop it immediately, and it always asks twice.

You changeWhile Claude is workingWhile Claude is idle
A step it hasn't startedRides the next tool result; a removed step's files are blocked onceRides your next message, or press Send now
The step it's onApplied after this step ends; Stop now (asks twice) if you can't waitApply now starts a short turn
Remove or reorderYour order and deletions win; Claude can't bring a removed step backSame, on your next message
A choice Claude madeThe map shows what gets redone ("redo Remember the login") before you confirmSent at once when finished work must change
Add a waypointDrawn dashed, "proposed by you", until Claude plans itRides your next message, or Start on it now

Every change carries a badge until Claude confirms it: queued ~, then delivered ✓ when Claude has read it, then acknowledged ✓✓ when its next update reflects it. If Claude doesn't acknowledge after two chances, the badge says so and offers Send now.

Item 5 · Ground rules

Honest first, then fun

The map always

  • Tells "checked" (a test it saw pass) apart from "done, not tested" (Claude's word only).
  • Says when it's stale: "Claude last checked in 3 min ago".
  • Tells waiting-for-you, thinking hard, and stuck apart from real events, never from silence.
  • Counts steps, never percentages or arrival times. When the route grows, the bar moves back and says why.
  • Keeps tool calls, commands and diffs out of sight unless you press details.

Fun is earned

  • The plane flies to the next step, cruises while Claude works, circles while it waits for you, shakes through turbulence, and lands at the flag.
  • A soft tick per checked step, a chime per finished waypoint, a cabin-chime knock when Claude needs you, a fanfare on landing. One sound per 2 s, one switch to mute.
  • Confetti only for work the map saw verified.

Never

  • Points, streaks, levels or speed scores.
  • Celebrating work nobody checked.
  • Dropping one of your edits without a badge saying so.

Item 7 · The contract

What Claude is told

Claude gets one tool, mcp__flightplan__route, with five operations, and a short note on each of your messages. Nothing about the live map goes into the system prompt, so it never invalidates Claude's prompt cache.

OpWhen Claude calls itCost
setOnce, when the shape of the work is clear: waypoints, steps, each step's files and check300–1,200 tokens, once
stepFinishing and starting steps, with evidence such as "node --test: 11 passed"~50 tokens
patchAdding, dropping, rewording or reordering steps it hasn't started~100 tokens
decideAny choice you didn't ask for: a library, a structure, a skipped step~80 tokens
getRe-reading the route after a long session is compacted~15 tokens per step
The note that rides each of your messages 
Flight Plan is on: the user follows this task on a live map. For work with two or more steps, keep it current with mcp__flightplan__route: set once, then step at every step boundary (finish + start in one call). Close the last step before you reply. Map now: step 4 of 9 in progress, s5 "Saving the login so it survives a refresh".
The tool description (1,901 of 2,048 characters) 
Flight Plan is the user's live map of this task: a side pane that draws your plan as a route of waypoints (features), the steps under each, and decisions, with a plane on the step you are on. The user watches this map, not your tool calls, and edits nodes there; their edits come back in this tool's results. Use it for any task with two or more steps, plan mode or not; never for one-off questions.

Wording comes first: write for someone who does not code. A title is the outcome in the user's words ("Let users log in with Google"), never a file, function or library name; why is one plain line. Paths go in files, commands in check.

Ops (field op): set, step, patch, decide, get (as above).

Every result carries version and userEdits: nodes the user renamed, removed, reordered, added or skipped, and decisions they flipped. Apply them before starting the next step, echo their ids in acks, and pass version back as baseVersion. On a conflict the user's wording, order and deletions win.
